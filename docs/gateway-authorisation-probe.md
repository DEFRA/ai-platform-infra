# Gateway authorisation probe

Proves design E verify 11 for the gateway authorisation layers (B23, HVE #42): the global policy's `on-error`,
`return-response` in the global `backend` section, and the `Jwt` members the checks read. Nothing here is applied
by hand: the probe is the P6 release itself, applied to Infradev through the platform and tenants applies, then
read-only calls.

## Verdict from Learn (checked 4 November 2026)

| Part of verify 11                                                                                     | Learn says                                                                                                                                                                                                                                                                                                                                                            | Source                                                                                                                                     |
| ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| A `validate-jwt` failure runs the global `on-error`, so it can add `WWW-Authenticate`                 | "If an error occurs, processing immediately jumps to the `on-error` policy section", usable at any scope, with `return-response` and `set-header` allowed there; `validate-jwt` failures are predefined errors (`TokenNotPresent`, `TokenSignatureInvalid`, `TokenAudienceNotAllowed`, `TokenExpired` and others), exposed as `context.LastError.Source` and `Reason` | [Error handling in API Management policies](https://learn.microsoft.com/en-us/azure/api-management/api-management-error-handling-policies) |
| `return-response` in the global `backend` section stops an ungranted request before `forward-request` | "cancels pipeline execution and returns either a default or custom response"; policy sections: inbound, outbound, backend, on-error; scopes include global                                                                                                                                                                                                            | [return-response](https://learn.microsoft.com/en-us/azure/api-management/return-response-policy)                                           |
| The allow-list includes `Jwt.Algorithm`, `Jwt.IssuedAt` and `Jwt.ExpirationTime`                      | The `Jwt` type exposes `Algorithm: string`, `ExpirationTime: DateTime?`, `IssuedAt: DateTime?`, `Claims` with `GetValueOrDefault(claim, default)`; `System.Nullable` is allowed in full, and `DateTime.AddHours` is on the allowed list                                                                                                                               | [Policy expressions](https://learn.microsoft.com/en-us/azure/api-management/api-management-policy-expressions)                             |
| `validate-jwt` has the settings the plan needs                                                        | `clock-skew` ("allowed clock skew in seconds", default 0), `require-scheme`, `issuers`, `openid-config` (keys cached for an hour, refetched at most every 5 minutes for an unknown `kid`), `output-token-variable-name` giving a `Jwt`                                                                                                                                | [validate-jwt](https://learn.microsoft.com/en-us/azure/api-management/validate-jwt-policy)                                                 |

Constraint 11 holds on the documentation, with no change to the design. The Learn pages do not say that the
global scope's `on-error` is the one that runs for a failure raised in the global `inbound`, or that a gateway
saves the new expressions; the probe below observes both.

## What the probe observes

Run by the Releaser after G3, in Infradev, in this order. Use a client-credentials token for the platform's
`api-aip-infradev` audience from a team's registration (never print or store it), and a team that exists there.

| Step | When                                               | Call                                                                                                     | Expect                                                                                                                           | Proves                                                                                                                                                      |
| ---- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Platform apply                                     | none                                                                                                     | The apply succeeds; API Management refuses a policy or fragment with a disallowed expression, so a failure here names the member | The `Jwt`, `DateTime` and `LastError` members are accepted (verify 11, part 3)                                                                              |
| 2    | After the platform apply                           | `GET /{team}/whoami` with no `Authorization`                                                             | 401 `{"code":"invalid-token"}` with `WWW-Authenticate: Bearer`                                                                   | A `validate-jwt` failure reaches the global `on-error` (part 1)                                                                                             |
| 3    | After the platform apply                           | The same call with a token for another audience, or a garbage one                                        | 401 `{"code":"invalid-token"}` with `WWW-Authenticate: Bearer error="invalid_token"`                                             | The reason is carried through (part 1)                                                                                                                      |
| 4    | After the platform apply, before the tenants apply | A chat call for a granted model, and `GET /{team}/whoami`, each with a valid token for the team's client | Both 403 `{"code":"client-not-granted"}`; the chat call has no backend call in Application Insights                              | `return-response` in the global `backend` stops an ungranted request (part 2); `whoami` fails closed too, because an old team policy never marks the caller |
| 5    | After the tenants apply                            | `GET /{team}/whoami` with a valid token                                                                  | 200 with the client, window and `credentialType` `oauth`                                                                         | G5 passes a real Entra app token: `azpacr` is present and not `0`, `idtyp` `app`                                                                            |
| 6    | After the tenants apply                            | A chat call for a granted model                                                                          | 200, and a call with an unlisted model gets 403 `model-not-granted`                                                              | The gate lets a marked request through                                                                                                                      |
| 7    | After the platform apply                           | `GET /{team}/whoami` with a valid token and an `Ocp-Apim-Subscription-Key` header (any value)            | 401 `{"code":"invalid-token"}` with `WWW-Authenticate`                                                                           | G3: a key on a token path is refused (AC15)                                                                                                                 |
| 8    | After the platform apply                           | The same call with `?subscription-key=x` in the query instead                                            | 401 `{"code":"invalid-token"}` with `WWW-Authenticate`                                                                           | G3, query form                                                                                                                                              |
| 9    | After the platform apply                           | The same call with an `Authorization` header of 8192 characters or more                                  | 401 `{"code":"invalid-token"}` with `WWW-Authenticate`                                                                           | G3: oversized header                                                                                                                                        |
| 10   | After the platform apply                           | `GET /research/whoami` with a valid Entra token and no key                                               | 401 from API Management's own subscription check (its default body, no code)                                                     | A token alone never reaches the Research tier (the API requires a subscription)                                                                             |
| 11   | After the platform apply                           | `GET /research/whoami` with a valid key and a valid Entra token                                          | 401 `{"code":"invalid-credential"}`                                                                                              | The key guard refuses a token on the Research path by policy (AC15)                                                                                         |
| 12   | After the platform apply                           | `GET /research/whoami` with a valid key only (a test person's key issued through the portal)             | 200 with `credentialType` `key`                                                                                                  | The key tier still answers, and `whoami` is marked by the key guard                                                                                         |

Record each result in the run's `plan.md` under T14. Steps 2 to 4 need no team change and step 4 happens naturally
between the two applies, while team policies still lack the team layer, so no caller is marked. Steps 7 to 12 are
the negative cases the Terraform tests cannot prove, because they only read the policy text.

## If a part fails

| Failure                                                        | Fallback, decided with the user                                                                                                                                                                                          |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `on-error` does not run, or the header is missing              | Keep the 401 and accept no `WWW-Authenticate` on `validate-jwt` failures (RFC 6750 asks for it, but the refusal is unchanged); the checks that return from the fragment keep their header. Record the gap in B23's notes |
| `return-response` is refused in the global `backend`           | Move the gate into `aip-backend-foundry`, the last inbound step of every team API, and have a check in `aip-checks` that every team API includes it; an API with no team policy would then need its own refusal          |
| A `Jwt` member or `DateTime` method is refused                 | Read `exp`, `iat` and the header through `Claims` (`exp - iat` in seconds) and drop the algorithm check, which `openid-config` keys and Entra's `RS256` signing already pin; record the loss of the explicit check       |
| `azpacr` is missing from federated tokens (design E verify 10) | G5 refuses every federated token: relax it to refuse only an `azpacr` of `0`, and record that a token with none is accepted                                                                                              |
| `clock-skew="60"` is read as something other than seconds      | Entra cannot mint an expired token to test it; compare a token near its end with the documented 60 seconds, or set the attribute as `00:01:00` if the gateway rejects `60`                                               |
